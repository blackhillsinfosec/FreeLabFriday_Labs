# C2 Basic Terminology & Theory

Before starting the hands-on C2 labs, we recommend reading this file first to become familiar with the basic terminology and theory behind C2 tools. Most of these terms and concepts are the same across most C2 frameworks, with a few minor exceptions.

## Basic Terminology

### Command and Control (C2)

Command and Control (C2) refers to the communication channel between an operator and a compromised machine. Through this communication channel, the operator is able to send commands to compromised machines and receive the desired information.

A C2 server is the central system that manages the C2 infrastructure. It is responsible for managing listeners, operators, implants, sessions, beacons, and collected results. It receives connections from implants, sends tasks or commands to them, and collects the returned data. The C2 server is managed by one or more operators.

The operator console connects to the C2 server and allows the operator to interact with it. Through the operator console, the operator can perform actions such as managing listeners, generating implants, issuing commands, and reviewing task results.

### Operator

The operator is the person using the C2 framework. The operator can be a penetration tester, red teamer, or attacker controlling the C2 infrastructure.

### Implant

An implant is a program generated by the C2 framework based on the specifications defined by the operator. It runs on the target machine and communicates with the C2 server. The implant receives tasks from the C2 server, executes them on the compromised machine, and sends the results back to the C2 server. Through this process, the operator is able to view the results of their actions.

Other tools may refer to implants as agents, payloads, beacons, or malware samples.

### Payload

A payload is a code or executable that is delivered and executed on the target machine. The payload usually contains the implant. After its execution, it connects back to the C2 server and gives control to the operator.

### Listener

A listener is a service running on the C2 server that waits for incoming connections from implants. These connections can be over different protocols such as HTTP, HTTPS, DNS, mTLS, or other protocols. A C2 server can have multiple listeners to serve different protocols. Without a listener, the implant wouldn't know where to connect.

### Callback

A callback is the signal that the implant sends to the C2 server after its execution on the target machine. Through this process, we understand that the implant is running correctly on our target machine and that the communication is working.

### Session

A session is an active connection between the implant and the C2 server. Sessions are usually interactive. This means that the operator can execute commands and receive the responses immediately. Sessions are useful when the operator wants to have direct interaction with the target machine.

### Beacon

A beacon is a type of implant communication where the implant checks in with the C2 server at specific time intervals. Unlike sessions, beacons operate asynchronously. The implant periodically contacts the server, asking for new tasks. This makes the communication slower, but it is also less noisy than a constant connection.

### Check-in

A check-in is when a beacon contacts the C2 server to report that it is still active and to ask for new tasks. For example, if the beacon is configured with a one-minute interval, it will check in with the C2 server every minute, ask for new tasks, and deliver the results of previous tasks if any exist.

### Task

A task is a command sent from the C2 server to the implant. In beacon mode, tasks may wait in a queue until the beacon checks in again.

### Stager vs Stageless Payloads

A stager is a small initial payload that runs first and then downloads or loads the rest of the implant from the C2 server.

A stageless payload contains everything it needs inside one file. It does not need to download any additional stage before running.

## Structure of a C2 Framework

A C2 framework is usually composed of several main components that work together to allow remote control of a target machine.

The main framework component is the C2 server, which acts as the main coordination point. The operator interacts with the C2 server through the operator console. Through this console, the operator can configure listeners, generate implants, issue tasks, and review returned results.

The C2 server uses one or more listeners to wait for incoming connections from implants.

On the target side, an implant runs on the target machine and communicates with the C2 server through one of the configured listeners. Once communication is established, the implant may appear as a session or a beacon, depending on how it is configured by the operator.

The operator sends tasks to the implant through the C2 server. The implant executes those tasks on the target machine and returns the results back to the C2 server. Then the operator can review them through the operator console.

## C2 Workflow

The following steps represent a basic C2 workflow.

1. The operator starts the C2 server.
2. The operator creates a listener.
3. The operator generates an implant.
4. The implant is delivered to the target machine through a predefined delivery mechanism.
5. The implant is executed on the target machine.
6. The implant connects back to the C2 server.
7. The operator receives a session or beacon.
8. The operator sends tasks or commands to the implant.
9. The implant executes the tasks on the target machine.
10. The implant sends the results back to the C2 server.
11. The operator reviews the returned results through the operator console.
